# 地图驱动的抓放架构 (Map-Driven Pick and Place)

**日期**: 2026-10-04
**状态**: 待评审 (rev 2)

## 背景

现在 `skills/pick_and_place.py` 的抓取阶段和放置阶段各有一份**相同的**四位姿扫描循环
（`pick_and_place.py:53` 和 `:148`），都从 `grasp1` 开始逐个走 `grasp1→grasp4`：

```python
for key, value in self.config.default_traj_js.items():
    if "grasp" not in key:
        continue
    self.control_arm(pose_type=key, speed=30)
    self.rgb, self.depth = self.get_camera_obs()
    ...
```

后果（2026-10-04 实测，放桃子进蓝盘子那一轮）：

- 抓完桃子时臂在 `grasp4`，**刚看见蓝盘子**；放置阶段却从 `grasp1` 重新开始，
  4 次移臂 + 4 次拍照 + 4 次 YOLO 去找几秒前就在看的东西。
- 前两个位姿是**必然白跑**的：日志里两条 `要 blue plate, 但只看到 {'pink'}; 颜色对不上, 不猜`
  就是白跑的证据。
- `core/scene.py` 的场景地图本来就是为这个写的，但它只在四位姿**全失败之后**才查
  （`pick_and_place.py:167`），而且平时是空的。

另有一个独立的运动问题：**腕部支路不统一**。`grasp1-4` 录制值 J4 ≈ -164…-172.5°，
离真机 ±177.96° 限位只剩 ~9°，抓取候选需要腕部转动时会被 IK 逼到 ZYZ 翻转分支，
而翻转分支要穿过 ±180° 的限位死区（J4 行程 355.92°，比整圈少 4°），孪生的 `BRANCH_JUMP`
保护因此正确地把候选判成不可达。

2026-10-04 的临时修法是 `Config.reload()` **只**把 `grasp*` 翻到 ZYZ 等价解。这**引入了
新的多余运动**：`home` 本身在 J4=-170.5（原支路），从 home 到翻转后的观察位姿要在腕上转
**179°**。实测对照：

| 路径 | 原支路 | 只翻 grasp*（当前） | 全表统一翻 |
|---|---|---|---|
| home → grasp1 | 38.9° | **178.9°** | 38.9° |
| home → place1 | 88.3° | 88.3° | 88.3° |
| home → handover_pose | 103.5° | 103.5° | 103.5° |

## 目标

1. **扫一次建图 → 直奔对的位姿 → 抓 → 放**。每个阶段只访问一个观察位姿，把重复移动
   压到最少。
2. **消除腕部支路跳跃**，"翻腕 / 360° 旋转"从根上消失。
3. **抓取只试一个候选**，失败即报失败退出。

## 非目标

- **不动真机做抓取验证**（本次只搭架构）。
- **不删检测**。长期路线是先让"抓准放准"稳住，再考虑去掉运行时检测；本设计是那条路线的
  第一段（用地图**选位姿**，不用地图**算位姿**）。
- **不做末尾回访确认**。已讨论并砍掉：由人看桌面即可，不值得引入一套成败判定逻辑。
- **不做自动扫描**。`look_around` 保持独立 skill，由调用方（人 / 未来的长线任务执行器）
  先跑；`pick_and_place` 不自己触发扫描。
- 不改 `robot_config.json` 里的录制数值（翻转只在内存里做）。

## 1. 角度规范化 vs 限位检查

这一节是整个改动最容易互相掣肘的地方，先把契约钉死。**两个概念严格分开，谁也不替谁兜底**：

### 1.1 纯算术规范化

```python
def fold(v, period):        # 纯算术, 不知道任何限位
    """折进 (-period/2, period/2]。"""
```

- 只看数学，不看真机。输入 `-179.5` 就返回 `-179.5`，**不**因为"这个角越限"而改成别的。
- 唯一的规范化函数，全仓只有这一份。

### 1.2 限位检查

```python
LIMITS = {"J1": 177.96, ..., "J5": 177.96, "J6": 359.82}   # 真机, 唯一来源

def within_limits(pose) -> bool:
    """每个关节是否落在真机限位内。越限就是越限, 不修不猜。"""
```

- 限位表只有一份，来自 `dependence/twin_inference/robot.py:wrap_joint_limits` 的注释。
- **J4 的死区**：J4 行程 355.92°（±177.96），比整圈少 4°，所以 `±180` 附近有 4° 的
  不可达缺口。`fold` 完全可能产出落在缺口里的值（如 `-179.5`）—— 那是 `fold` 的本分，
  由 `within_limits` 报出来，**不允许 `fold` 私自把它挪到别处**。

### 1.3 ZYZ 翻转：每个关节各自怎么处理

翻转是 `(J4, J5, J6) → (J4+180, -J5, J6+180)`，对合，且是腕关节空间上的**等距变换**：
两个位姿一起翻，J4 与 J6 的差不变、J5 的差只变号，所以**两两相对距离逐个保持不变**。
上表 home→grasp1 的 38.9°→38.9° 就是这个性质 —— 全表一起翻不新增任何运动。

但三个关节的规范化**必须不同**，理由是各自的限位宽度不同。判据是一条：

> **折的周期必须让结果落在该关节的限位之内。**

| 关节 | 限位 | 翻转后怎么处理 | 为什么 |
|---|---|---|---|
| J4 | ±177.96（**有 4° 死区**） | `fold(J4+180, 360)` **且** 落进 `[-90,90]` | 折 360 的结果域 (-180,180] **超出**限位 —— 例如折出 `-179.5`，正好落进死区。所以 J4 不能只靠折，必须有"余量带"这第二个约束 |
| J5 | ±177.96 | 直接取负，**不折** | 合法值的相反数仍合法，无需折 |
| J6 | ±359.82 | `fold(J6+180, 360)` | 结果域 (-180,180] **含于**限位，折 360 就够了 |

这就是"规范化与限位不要互相掣肘"的实际内容：**`fold` 只管数学，落点是否合法由限位决定；
J4 因为限位比一个整圈窄 4°，所以额外需要余量带；J6 因为限位比一个整圈宽，折 360 就够。**

三条都能证明翻转后必合法：J4 落 `[-90,90]` ⊂ ±177.96 ✓；J5 取负保号 ✓；
J6 落 `(-180,180]` ⊂ ±359.82 ✓。**但这是要测的性质，不是 `fold` 的保证** —— 所以
`within_limits` 仍然要独立存在并单独测。

跨位姿的**行程**另算：J1–J5 不能环绕（限位挡住），J6 可以。孪生的
`robot.py:joint_dist` 已经只对 J6 做环绕，**这是对的**，见 1.5。

### 1.4 幂等（reload 时必须成立）

`wrist_headroom_pose` 的早退条件是 `abs(J4) <= 90`。翻转把 `(90,180] → [-90,0)`、
`[-180,-90) → (0,90]`，落点必然在 `[-90,90]`，所以**再翻一次不动** —— 幂等由构造保证，
不靠调用方小心。

- `Config.reload()` 可以对同一份数据反复调用，结果一致。
- 幂等性**必须有测试**：全表 + 边界值（`±90`、`±180`、`±177.96`、`0`）逐个验
  `f(f(p)) == f(p)`。

### 1.5 孪生那一侧的限位处理（不改，但要在 spec 里说清是有意的）

`dependence/twin_inference/robot.py` 有自己的三个函数，契约不同，**不要混用**：

- `wrap_joint_limits(js)`：值落进死区时返回 `None`。**这是正确的** —— 死区就是不可达。
- `joint_dist(a, b)`：**故意只对 J6 做环绕**，J4 不环绕。因为 J4 的短路被死区挡着，
  真机上确实要走 340.9°。这是有意为之，不是漏了。
- `enforce_joint_limits(js, ref)`：构造平凡环绕和 ZYZ 翻转两个候选，取离 `ref` 近的那个。

**契约**：`core/config.py` 负责"存进去的值合法且有余量"，`twin_inference` 负责"从当前
关节角到目标关节角怎么走"。两边共用同一份限位数值，但**各自不替对方做决定**。

## 2. 地图驱动选位姿

`look_around` 建图时每条记录带 `seen_from`（哪些观察位姿看见过它）。用它选位姿：

- **抓取阶段**：`scene_map.find(map, name, color)` → 取 `seen_from[0]` → 只去那一个位姿，
  在那儿拍照、跑 AnyGrasp、抓。
- **放置阶段**：同样查容器 → 只去那一个位姿，在那儿检测、算放置点。
- **取哪个位姿**：`seen_from[0]`。`scene_map.merge` 按扫描顺序追加，所以 `[0]` 就是
  `grasp1→grasp4` 里**最先**看见它的那个，也就是走路最少的那个。
- **回退**：地图里没有该目标 → 走现有的四位姿循环（**保留不删**，作为保底）。

本阶段只用地图的 `seen_from` 选位姿。**放置阶段**另外用地图记的世界坐标当落点
（`_placing_position_from_scene`）：现场那个框可能被画面边缘切掉而算不出中心，地图的
世界坐标不受当前视角影响，反而更稳。抓取阶段不用地图坐标 —— 抓取位姿必须来自当场
的 AnyGrasp。

### 2.1 地图命中之后，现场检测必须能证实它

去了那个位姿、当场检测，**必须确认地图的说法**。以下任何一条成立就算"出问题"：

1. 现场**完全没检出**目标（地图说有）。
2. 现场检出的**颜色**与地图记录不符。

**核对必须用建图那一套检测**（`scene.scan_workspace` 里 `detect` 回调用的
`detect_scene`：YOLO 认 `SCAN_VOCAB` 里的名词 + 颜色从框内像素取）。换用容器的
`detect_container` 会多一层 `_well_framed` 过滤（框被画面切掉就丢掉），把"画面边缘的框"
误报成"东西被挪了"——停下问一个不存在的问题。

**出问题的处理：立刻停下，把话说清楚，交给人。**

- 打印一行明确的对照：地图说 `蓝 plate` 在 `grasp4`（扫描于 11:38），现场在 `grasp4`
  只看到 `粉 plate` —— 请你确认是东西被挪了还是地图过期。
- 技能 `return False`，**不猜、不自动回退、不换下一个位姿**。
- 理由：回退到四位姿循环正是这次要消灭的"重复移动"，而且它会把"地图错了"这个信号
  悄悄吃掉，下次还是错的。

## 3. 建图：独立 skill，不是 pick_and_place 的一部分

`look_around` 保持独立 skill。调用顺序是**先 `look_around`，后 `pick_and_place`**，
由人（或未来的长线任务执行器）编排。`pick_and_place` **不自己触发扫描**。

`pick_and_place` 对地图的处理：

- 地图**存在且新鲜** → 用 `seen_from` 选位姿。
- 地图**不存在或过期** → 打印"请先跑 `look_around`"，`return False`。
  **不走四位姿循环** —— 那样等于把"没建图"这个事实藏起来。

"新鲜"由 `SCENE_MAP_TTL_S`（新常数，默认 300 秒）判定，比较 `scene.json` 的 mtime。

**实现约束（CLAUDE.md 硬规矩）**：流水线执行中**禁止跨 Skill 实例化**（新实例会另开
arm/hand 的 TCP 连接，破坏阶段衔接）。所以共享的扫描逻辑**不能**是 `LookAroundSkill()`，
必须抽成**函数**。

### 3.1 共享函数的契约

从 `look_around.py` 提出去，放 `core/scene.py`（不持有硬件，只接收句柄）：

```
scan_workspace(move_to_pose, capture, transform, detect, poses) -> list[entry]
```

| 参数 | 类型 | 契约 |
|---|---|---|
| `move_to_pose` | `(name) -> None` | 把臂移到该观察位姿并**阻塞到到位** |
| `capture` | `() -> (rgb, depth)` | 返回**当前**位姿下的一帧；**不负责**刷新坐标变换 |
| `transform` | `() -> None` | 刷新"基座←相机"变换。**每个位姿必须调一次** |
| `detect` | `(rgb) -> list` | 返回该帧的检测框 |
| `poses` | `list[str]` | 要扫的观察位姿，**按顺序** |

- 返回：`entry` 列表，每项含 `name` / `color` / `world` / `conf` / `seen_from`，
  **不合并、不落盘** —— 合并与落盘仍由调用方做（`look_around` 走 `scene_map.merge` + `save`）。
- **`transform` 必须每帧调一次**：`T_base_to_cam` 随臂动，沿用上一个位姿会让所有世界
  坐标都算错。这是现有代码里已经踩过的坑（`look_around.py:33-35` 的注释），抽函数时
  **不能让调用方有机会漏掉** —— 所以把它做成独立入参而不是塞在 `capture` 里。
- 自动路径**不跑 VLM**。VLM 那段的产出是给人读的场景描述，对建图没用，又慢又花钱。

## 4. 拆词

现在 `_placing_position_from_scene` 用 `words[0]` 当颜色、`words[-1]` 当名词，是硬编码
的位置约定。换成 `core/` 里的一个小解析器：

```
parse_target(phrase, color_vocab, noun_vocab) -> (color | None, name)
```

规则（按顺序）：

1. 取词。若**首词**在 `color_vocab` 里、且**剩余部分**在 `noun_vocab` 里 → 拆成
   `(首词, 剩余部分)`。`"blue plate"` → `("blue", "plate")`。
2. 否则**不拆**，整串当名字。`"red fruit"` → `(None, "red fruit")` —— 因为 `"fruit"`
   不在名词表里，而 `red fruit` 是 YOLO-World 认得出的**单个类名**，拆了反而查不到。
3. 多词颜色（`"light blue"`）暂不支持，等真出现再说。

`color_vocab` / `noun_vocab` 是**现场标定**的小词表，和白平衡常数 (`CAMERA_WHITE_BALANCE`)
同一性质 —— 换场景要重探。留一个 `tools/probe_vocab.py` 做重探。

**关于"其他类别也要分清楚"**：目前只做**颜色 + 名词**两档。再往上（尺寸、材质、形状）
现在没有真实的混淆案例支撑，加了只会让词表变长、标定变重 —— 按"图中造成混淆的几率比较
小就舍弃细分度"的原则，**先不做**，等真的出现两个同名同色、必须靠第三个属性区分的东西
再加。

实测可用的词（2026-10-04，这张桌子）：

| 物体 | 可用词 | 置信度 | 不可用 |
|---|---|---|---|
| 桃子 | `plum` | 0.836 | `peach` 只有 0.325；`nectarine` 会误匹配粉盘子 |
| 火龙果 | `pitaya` | 0.166 | `dragon fruit` **零检测**；`red fruit` 从 grasp1 会匹配到橙子 |
| 黄瓜 | `cucumber` | 0.906 | — |
| 橙子 | `orange` | 0.665 | `red fruit` 同框 |
| 柠檬 | `lemon` | 0.761 | — |

## 验证方案（不动真机）

1. **角度契约**（纯函数，最容易测）
   - `fold` 的纯算术行为：`-179.5 → -179.5`（不因越限而改）。
   - `within_limits`：J4 = ±179 判越限（死区内）；J6 = 380 判越限；合法值判合法。
   - **幂等**：全表 + 边界值（`0, ±90, ±177.96, ±180`）逐个验 `f(f(p)) == f(p)`。
   - **等距**：翻转前后，全表**任意两两**位姿的腕部相对距离逐对相等。
   - **折的落点在限位内**：J4 用 `fold(...,360)` 能折出 `-179.5`（越限，死区），
     所以额外要验 `abs(J4) <= 90`；J6 折 360 的落点 `(-180,180]` 恒在 ±359.82 内。
   - 全表翻转后 `abs(J4) <= 90`，且全部 `within_limits`。
2. **地图与拆词**
   - `parse_target`：`"blue plate"` → `("blue","plate")`；`"red fruit"` → `(None,"red fruit")`；
     `"trash"` / `"person"` / `"desk"` 走特殊模式分支，不进解析器。
   - `pick_and_place` 在假地图下选出 `seen_from[0]`。
   - 空地图 / 过期地图 → 报"请先跑 look_around"并 `return False`，**不走四位姿循环**。
   - 现场检测与地图不符的三种情形，各自触发"停下问人"。
3. **共享函数契约**
   - `scan_workspace` 用假句柄测：断言 `transform` 被调用次数 **== 位姿数**（不能少）。
   - 断言返回的 entry 未合并、未落盘。
4. **纯计算验证**（不需要臂动）
   - 用孪生的正向运动学验：翻转前后每个位姿的 `link_6` 位姿一致。
5. **不做的**：真机抓取、真机移动。

`tests/test_observation_pose_branch.py::test_config_flips_observation_poses_but_not_others`

## 风险

| 风险 | 说明 | 处理 |
|---|---|---|
| 翻转后的 home/place/handover 姿态可能撞桌 | `move_to_named_pose` 走 movej，**不过孪生的碰撞检查** | 下次上真机时按 `grasp1-4` 那样慢速逐个验末端位姿；本设计不动真机 |
| 地图过期 | 建图后东西被移动 | TTL 判定 + 现场检测证实，不符就停下问人 |
| 地图词表对不上用户说法 | 用户说"桃子"，地图里是 `plum` | 词表统一到指令词；`tools/probe_vocab.py` 重探 |
| 共享函数漏刷坐标变换 | 世界坐标全错，但日志看不出来 | `transform` 做成独立入参 + 测试断言调用次数 |

## 未决

- `SCENE_MAP_TTL_S` 默认 300 秒是拍的，真机上要试多久合适。
- "停下问人"目前实现为**打印 + `return False`**（`run_skill.py` 的 stdin 被 JSON 占用，
  阻塞式 `input()` 读不到东西）。若以后要交互式确认，走 `/dev/tty`。
